## 작업 계기

현재 운영 중인 서비스에서는 Sentry를 도입한 뒤 사내 메신저인 Slack과 연동해 에러가 발생하면 즉시 알림이 오도록 구성해 두었습니다.

이와 별개로 개인적으로는 Sentry MCP를 활용해 이슈 트래킹과 코드 탐색을 돕는 에러 추적 플러그인을 만들어 사용하고 있었습니다.

그러다 몇 주 전, 자체적으로 진행하던 서포터즈 활동 중 특정 기능에서 갑작스러운 에러가 발생했고, 원인을 찾기 위해 Sentry와 서버 로그를 오가며 꽤 많은 시간을 쏟은 일이 있었습니다.

알고 보니 사용자가 규격에 맞지 않는 값을 제출했을 때 토스트 알림을 띄워 주는 정상적인 흐름이었는데, API 응답값을 처리하는 내부 어댑터 코드에서 불필요하게 Crashlytics와 Sentry로 에러를 전송하고 있던 문제였습니다.

사용자에게 직접적인 영향은 없는 이슈였지만 원인을 파악하기까지 적지 않은 시간을 써야 했고, 특히 노트북을 사용할 수 없는 상황에서 처음 알림을 접해 추적하는 데 꽤 애를 먹었습니다.

이 일을 계기로 에러 알림이 왔을 때 최소한 원인 파악만큼은 빠르게 끝내고, 그 내용을 팀원들과 함께 공유할 수 있어야겠다는 필요성을 느꼈습니다. 그래서 개인적으로 쓰던 흐름을 확장해 사내 환경에 직접 구축하게 되었습니다.

## 확장

원인 분석 에이전트를 운영하다 보니 자연스럽게 아쉬운 점이 생겼습니다. 원인 파일과 줄 번호까지 정확히 짚어 주더라도, 결국 사람이 직접 파일을 열어 수정하고 테스트한 뒤 PR을 올려야 했습니다. 원인이 명확하고 수정 범위가 작은 버그라면 그 과정까지 맡겨 볼 수 있겠다고 판단했습니다.

그래서 원인 분석 결과가 **코드 결함, 확신 보통 이상**으로 나오면 같은 실행 안에서 수정 에이전트가 이어서 동작하도록 확장했습니다. 결과물은 `staging` 브랜치를 대상으로 한 **draft PR**이며, 최종 리뷰와 병합 판단은 사람이 맡습니다.

이때 세운 핵심 원칙은 **증거가 없으면 PR을 만들지 않는다**는 것이었습니다.

에이전트가 "고쳤다"거나 "수정이 필요하다"고 말로만 주장하는 것은 신뢰하기 어렵다고 생각했습니다. 그래서 코드를 수정하기 전에 버그를 재현하는 테스트부터 작성하게 하고, 재현·수정 검증·PR 검사·배포 후 확인을 아래 순서로 진행하도록 구성했습니다.

| **단계** | **확인하는 것** | **기대 결과** |
| --- | --- | --- |
| 버그 재현 | 수정 전 코드에서 재현 테스트를 실행합니다. | **실패** |
| 수정 확인 | 코드를 수정한 뒤 같은 테스트를 다시 실행합니다. | **통과** |
| 스테이징 재현 | 현재 스테이징(수정 전 코드)에서도 테스트가 실패하는지 확인해, 진짜 버그를 잡는 테스트인지 검증합니다. | **실패** |
| PR 검사 | lint, 타입 검사, 관련 테스트를 실행합니다. | 통과 |
| 배포 후 확인 | `staging`에 병합·배포한 뒤 재현 테스트와 스모크 테스트 전체를 실행합니다. | 통과 → `staging-verified` |

이처럼 실패 현상을 먼저 재현해 검증하고, 수정 후 테스트가 통과하는지 확인하는 구조로 안정성을 확보했습니다.

### 에이전트 밖의 안전장치

원인 분석 때와 마찬가지로, 에이전트에게 맡길 영역과 코드·규칙으로 통제할 영역을 명확히 구분했습니다.

- **규칙 검사**: 에이전트가 수정을 마치면 AI가 아닌 스크립트가 변경 내용을 다시 검증합니다. 변경 범위가 파일 5개나 200줄을 넘거나, 포인트·결제·출금 같은 민감한 도메인 코드 및 배포 설정을 건드리거나, 허용된 폴더 밖에 파일을 생성하면 PR을 만들지 않고 즉시 멈춥니다. 중단된 사유는 같은 Slack 스레드에 남깁니다.
- **중요 로직은 원인 분석까지만**: 민감한 영역에서 발생한 에러는 원인 분석 답글에 "수동 확인 필수" 표시가 붙으며, 수정 에이전트는 실행되지 않습니다.
- **PR 생성은 별도 작업으로 분리**: 에이전트가 실행되는 단계에는 쓰기 권한을 부여하지 않아 잘못된 push나 PR 생성을 원천 차단했습니다. 실제 push와 PR 생성은 별도의 GitHub App 토큰을 사용하는 후속 작업에서 처리하도록 분리했습니다.

### 실제 예시

PDF 뷰어에서 같은 canvas에 렌더링이 겹쳐 에러가 발생하던 이슈가 실제로 아래 흐름으로 처리되었습니다.

1. 🔍 반응 → 원인 분석: 디바운스 없는 `resize` 리스너가 이전 렌더링이 끝나기 전에 다시 렌더링을 시작하는 문제로 파악
2. 재현 테스트 실패 → 코드 수정 → 같은 테스트 통과
3. 규칙 검사 통과 → draft PR 생성 (🔍 반응부터 **19분** 소요)
4. 사람이 `staging`에 병합 → 스테이징 배포 → 스모크 테스트 33개 전부 통과 → `staging-verified` 라벨 부착

![PDF 뷰어의 canvas 중복 렌더링을 수정한 PR에서 재현 테스트가 수정 전 실패하고 수정 후 통과한 모습](/images/obsidian/self-healing-pr-agent/pr-agent-pdf-viewer-fix.png)

## 도입 결과

원인 추적 에이전트를 구축한 뒤 두 달 동안 웹과 앱 레포지토리에서 사용된 이력을 GitHub Actions 실행 기록과 Sentry 데이터를 통해 확인해 보았습니다.

### 원인 파악 시간

| **항목** | **결과** |
| --- | --- |
| 원인 분석 실행 | 35건 성공 (웹·앱 합산) |
| 분석한 이슈 | 18개 (웹 7건, 앱 11건) |
| 알림부터 원인 답글까지 | **중앙값 약 4분** (34건 기준, 최장 6분 45초) |
| 🔍 반응부터 수정 PR까지 | **19분** |
| 실행당 비용 | 약 \$0.5\~1 (구독 토큰 사용) |

예전에는 알림이 오면 Sentry를 열어 스택 트레이스를 확인하고, 최근 배포 이력과 대조해 가며 코드를 직접 살펴봐야 했습니다. 중간에 AI의 도움을 받더라도 팀원들에게 상황을 정리해 공유하기까지는 시간이 지체되는 경우가 많았습니다.

지금은 알림에 이모지 하나만 달아 두면 4~5분 뒤에 이슈 분류, 원인 파일과 줄 번호, 다음 할 일이 스레드에 올라옵니다. 물론 분석 결과가 정확한지 최종 판단은 개발자가 직접 내려야 하지만, 그 판단에 도달하기까지의 시간이 대폭 줄어들었습니다.

무엇보다 노트북이 없거나 코드를 바로 열어볼 수 없는 상황에서도 Slack 앱만으로 원인을 확인할 수 있게 되었습니다. 처음 이 작업을 시작하게 만든 불편함을 제대로 해소한 셈입니다.

### 한계

운영해 보면서 정확도나 시스템 구조 측면에서 아쉬운 점도 분명히 드러났습니다.

#### 에이전트가 틀릴 수 있다

실제 운영 중 사람이 교차 검증했을 때 에이전트가 잘못 분석한 사례도 있었습니다. 이미 수정된 버그를 다시 고쳐야 한다고 판단하거나, 배포와 무관한 이슈를 배포 탓으로 추정한 경우였습니다.

이를 개선하기 위해 사내 플러그인 마켓플레이스의 분석 지침을 코드처럼 관리하기 시작했습니다.

- 오진이 발생하면 오진 기록 문서에 "왜 틀렸는지"를 한 줄로 남깁니다.
- 그 원인을 분석 지침의 규칙으로 추가합니다. 실제로 *"수정 이력을 먼저 대조할 것"*, *"배포 탓으로 판단하려면 시간 근거를 제시할 것"*이라는 두 가지 규칙이 이런 과정을 거쳐 추가되었습니다.
- 지침 버전을 올리고 CHANGELOG에 기록한 뒤, 같은 에러로 다시 실행해 오진이 교정되는지 확인했습니다.
- 교정된 사례는 회귀 테스트 기준으로 남겨 두어, 앞으로 지침을 수정할 때마다 같은 실수가 재발하지 않는지 검증하는 데 활용합니다.

#### 수정 범위와 주요 코드 판정 기준

에이전트가 수정할 수 있는 범위는 의도적으로 좁게 잡았습니다. 아직 검증 단계이기도 하지만, 결제나 포인트 지급 같은 핵심 로직을 건드렸을 때 사람이 미처 놓치면 큰 장애로 이어질 수 있기 때문입니다.

특히 어떤 코드가 핵심 로직인지 판단하는 기준 자체를 에이전트에게 맡기지 않으려 했습니다. 대신 팀이 이미 합의해 둔 기준을 최대한 활용하고자 했습니다.

사내 마켓플레이스에는 코드 리뷰 플러그인 등 여러 도구가 함께 참조하는 레포지토리별 ADR이 있습니다. 이 ADR이 다루는 영역을 중심으로 수정 금지 경로를 설정했고, 주요 정책 문서와 관련된 경로도 추가로 지정해 신중하게 다뤄지도록 했습니다.

그 결과 사람이 문서로 합의한 기준과 에이전트가 따르는 기준이 하나로 일치하게 되었습니다. 새 ADR이 추가되면 정책 파일 한 곳만 업데이트하면 됩니다. 다만 여러 문서 간의 연관성을 파악하는 흐름은 앞으로 더 다듬어 나가야 할 부분입니다.

#### 알림이 오지 않는 문제는 볼 수 없다

이 시스템은 Sentry 알림을 기점으로 동작하기 때문에, 애초에 에러 알림이 발생하지 않는 문제는 감지할 수 없습니다. 또한 알림이 오더라도 개발자가 반응을 달아 워크플로우를 실행하지 않으면 추적이 시작되지 않습니다.

환불 금액이 잘못 계산되거나 푸시 알림이 발송되지 않는 경우처럼, 서버는 정상 응답을 반환했지만 비즈니스 결과가 틀린 경우가 대표적입니다.

그래서 에러가 터지길 기다리는 대신, **"이 기능은 이렇게 동작해야 한다"는 약속을 먼저 정의하고, 그 약속이 지켜지는지 스테이징에서 주기적으로 검증하는 테스트**를 만들기 시작했습니다. 약속 목록은 레포지토리에 파일로 관리하고, 깨진 약속은 기존과 같은 Slack 및 PR 흐름으로 보고됩니다. 마켓플레이스에는 이 결과를 여러 관점에서 다시 검토하는 플러그인(`op-promise-review`)도 추가했습니다. 에러 로그로 드러나지 않는 문제까지 에이전트가 볼 수 있는 신호로 만드는 것이 다음 목표입니다.

## 마치며

이 작업의 출발점은 "알림이 왔을 때 원인만큼은 빨리 알고 싶다"는 작은 불편함이었습니다. 솔직히 '이게 정말 될까?' 하는 실험적인 호기심도 한몫했습니다.

돌아보면 에이전트가 가장 크게 바꾼 것은 원인 조사의 출발점이었습니다. 또한 누가 조사하는지와 상관없이 팀 전체가 같은 정보를 보고 함께 판단할 수 있게 된 것도 큰 변화였습니다.

결과적으로 처음 원했던 목적은 충분히 달성했고 팀 내 만족도도 높았습니다. 하지만 여전히 개선할 여지도 많습니다.
