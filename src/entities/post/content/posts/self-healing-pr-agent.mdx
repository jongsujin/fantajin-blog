## 작업 계기

현재 운영 중인 서비스에서 Sentry 도입 후 사내 메신저로 활용하고 있는 Slack과 연동하여 에러 시 알림이 오도록 되어 있습니다.

추가로 개인적으로 Sentry MCP를 통해 이슈 트래킹 및 코드 탐색 등을 통해 에러 추적 기능의 플러그인을 만들어 사용하고 있습니다.

몇 주 전 자체적으로 진행하고 있는 서포터즈 활동 중 특정 기능에서 갑작스런 에러가 발생했고 이를 찾기 위해 Sentry와 서버 로그 등을 보며 많은 시간을 쏟았던 일이 있었습니다.

원인은 사용자가 규격에 맞지 않는 값을 제출했을 때 토스트 알림을 보여 주는 정상적인 흐름이었지만, 내부 코드 API 응답값을 정의하는 어댑터에서 Crashlytics 및 Sentry로 에러 알림을 보내고 있던 문제였습니다.

사용자에게 직접적으로 영향이 있던 부분은 아니었으나 이를 찾기 위해 많은 시간을 할애해야 했으며 특히 노트북을 사용할 수 없던 상황에서 처음 발견했던 거라 이를 추적하는데 꽤 고생을 했습니다.

그래서 알림이 왔을 때 적어도 원인 파악만큼은 빠르게 하면서 이를 팀원이 함께 공유할 수 있어야 한다는 필요성을 느끼게 되었고 개인적으로 사용하고 있던 프로세스를 확장해 사내 환경에 구축했습니다.

## 확장

원인 분석 에이전트를 쓰다 보니 아쉬운 점이 생겼습니다. 원인 파일과 줄까지 정확히 알려 줘도, 결국 사람이 그 파일을 열어 고치고 테스트하고 PR을 올려야 했습니다. 원인이 분명하고 수정 범위가 작은 버그라면 그 과정까지 맡길 수 있겠다고 판단했습니다.

그래서 원인 분석 결과가 **"코드 결함, 확신 보통 이상"**으로 나오면 같은 실행 안에서 수정 에이전트가 이어서 돌도록 확장했습니다. 결과물은 staging 브랜치 대상의 **draft PR**이고, 병합에 대한 판단과 리뷰는 사람이 합니다.

핵심 원칙은 **증거가 없으면 PR을 만들지 않는다**는 것이었습니다.

에이전트가 고쳤다, 수정이 필요하다라고 말하는 것만으로는 믿을 수 없다고 생각했습니다. 그래서 고치기 전에 버그를 재현하는 테스트부터 만들게 하고, 재현과 수정 검증, PR 검사, 배포 후 확인을 아래 순서로 진행했습니다.

| **단계** | **확인하는 것** | **기대 결과** |
| --- | --- | --- |
| 버그 재현 | 고치기 전에 재현 테스트를 돌린다 | **실패** |
| 수정 확인 | 고친 뒤 같은 테스트를 돌린다 | **통과** |
| 스테이징 재현 | 지금 스테이징(고치기 전 코드)에서도 테스트가 실패하는지 본다. 진짜 버그를 잡는 테스트인지 확인하는 단계 | **실패** |
| PR 검사 | lint, 타입 검사, 관련 테스트 | 통과 |
| 배포 후 확인 | staging에 머지·배포한 뒤 같은 테스트와 스모크 테스트 전체 | 통과 → `staging-verified` |

실패 현상을 재현하여 검증하고 수정을 통해 통과시키는 구조로 작업을 진행했습니다.

### 에이전트 밖의 안전장치

원인 분석 때와 마찬가지로 에이전트가 할 수 있는 일과 코드나 규칙으로 할 수 있는 일을 구분했습니다.

- **규칙 검사.** 에이전트가 수정을 끝내면 AI가 아닌 스크립트가 바뀐 내용을 다시 검사합니다. 파일 5개나 200줄을 넘기면, 포인트·결제·출금 같은 돈 관련 코드나 배포 설정을 건드리면, 허용된 폴더 밖에 파일을 만들면 PR을 만들지 않고 멈춥니다. 멈춘 이유는 같은 Slack 스레드에 남깁니다.
- **중요 로직은 원인 분석까지만.** 해당 영역의 에러는 원인 분석 답글에 "수동 확인 필수" 표시가 붙고, 수정 에이전트는 시작하지 않습니다.
- **PR 생성은 별도 작업으로.** 에이전트가 도는 단계에서는 쓰기 권한이 없도록 하여 잘못된 push와 PR 생성이 이루어지지 않도록 했습니다. 해당 작업들은 별도의 GitHub App 토큰으로 진행하도록 했습니다.

### 실제 예시

PDF 뷰어에서 같은 canvas에 렌더링이 겹쳐 에러가 나던 이슈가 아래와 같은 흐름으로 처리됐습니다.

1. 🔍 → 원인 분석: 디바운스 없는 resize 리스너가 이전 렌더링이 끝나기 전에 다시 렌더링을 시작함
2. 재현 테스트 실패 → 수정 → 같은 테스트 통과
3. 규칙 검사 통과 → draft PR 생성 (🔍부터 **19분**)
4. 사람이 staging에 머지 → 스테이징 배포 → 스모크 33개 전부 통과 → `staging-verified`

![PDF 뷰어의 canvas 중복 렌더링을 수정한 PR에서 재현 테스트가 수정 전 실패하고 수정 후 통과한 모습](/images/obsidian/self-healing-pr-agent/pr-agent-pdf-viewer-fix.png)

## 도입 결과

원인 추적 에이전트를 만들고 나서 두 달 동안 웹과 앱 레포에서 쓰인 기록을 GitHub Actions 실행 기록과 Sentry로 확인했습니다.

### 원인 파악 시간

| **항목** | **결과** |
| --- | --- |
| 원인 분석 실행 | 35건 성공 (웹·앱 합산) |
| 분석한 이슈 | 18개 (웹 7, 앱 11) |
| 알림부터 원인 답글까지 | **중앙값 약 4분** (34건 기준, 가장 길었던 경우 6분 45초) |
| 🔍부터 수정 PR까지 | **19분** |
| 실행당 비용 | 약 \$0.5\~1 (구독 토큰 사용) |

예전에는 알림이 오면 Sentry를 열고 스택을 확인하고 최근 배포와 맞춰가며 코드를 확인했어야 했습니다. 물론 AI의 도움을 받긴 하지만 실제로 팀원들에게 공유되는 과정까지 시간이 지체되는 경우들이 많았습니다.

지금은 알림에 이모지 하나만 달면 4\~5분 뒤에 분류, 원인 파일과 줄, 다음 할 일이 스레드에 올라옵니다. 물론 추가로 정확한지 판단은 개발자가 직접 해야 하지만 판단까지 걸리는 시간이 대폭 줄었습니다.

가장 중요한 것은 노트북이 없거나 지금 코드를 볼 수 없는 상황에서도 Slack 앱만 있으면 원인을 받아볼 수 있게 됐습니다. 이 작업을 시작한 계기였던 상황을 해결할 수 있게 되었습니다.

### 한계

정확도나 시스템적으로 아쉬운 점도 존재했습니다.

#### 에이전트가 틀릴 수 있다.

실제로 테스트 과정 중 사람이 맞는지 확인한 건 중 잘못 판단한 분석도 존재했습니다. 이미 고친 버그를 다시 고쳐야 한다고 하거나, 배포 문제가 아닌데 배포 탓으로 추정한 경우였습니다.

이를 개선하기 위해 사내 플러그인 마켓플레이스의 분석 지침을 코드처럼 관리했습니다.

- 오진이 나오면 오진 기록 문서에 "왜 틀렸나"를 한 줄 남깁니다.
- 그 이유를 분석 지침에 규칙으로 추가합니다. 실제로 "수정 이력을 먼저 대조할 것", "배포 탓으로 판단하려면 시간 근거를 제시할 것" 두 규칙이 이렇게 들어갔습니다.
- 지침 버전을 올리고 CHANGELOG에 남긴 뒤, 같은 에러로 다시 돌려 교정되는 것을 확인했습니다.
- 교정된 사례는 회귀 기준으로 남겨, 지침을 바꿀 때마다 같은 실수가 다시 나오지 않는지 확인하는 기준으로 씁니다.

#### 수정 범위와 사람이 판단해야 할 주요 코드 판정

에이전트가 고칠 수 있는 범위는 의도적으로 좁게 잡았습니다. 테스트 과정이기도 하지만 결제나 포인트 지급 같은 주요 로직을 건드릴 때 사람이 놓쳤을 때 큰 영향이 있을 수 있기 때문입니다.

특히 주요 로직을 판단하는 기준을 에이전트에게 판단하지 않게 하려고 노력했습니다. 팀이 이미 합의해둔 기준을 최대한 활용하고자 했습니다.

사내 마켓플레이스에는 코드 리뷰 플러그인 등 플러그인들이 공유하는 레포별 ADR이 있습니다. 이 ADR이 다루는 파트를 위주로 금지 경로로 설정했고 주요 정책 문서 같은 것들은 추가로 경로를 지정하여 최대한 유의하도록 했습니다.

그 결과 사람이 문서로 합의한 기준과 에이전트가 지키는 기준이 같아졌습니다. 새 ADR이 생기면 정책 파일 한 곳만 고치면 됩니다. 다만 문서들 간의 연관성을 파악하는 플로우는 좀 더 개선이 필요한 부분이기도 합니다.

#### 알림이 오지 않는 문제는 볼 수 없다.

Sentry 알림으로 시작하기 때문에 Sentry 알림이 오지 않는 것들은 파악할 수 없었고 알림이 오더라도 개발자가 워크플로우를 실행하지 않으면 추적하지 않습니다.

환불 금액이 잘못 계산되거나 알림이 발송되지 않는 경우처럼, 서버는 정상 응답을 했지만 결과가 틀린 경우입니다.

그래서 에러를 기다리는 대신 **"이 기능은 이렇게 동작해야 한다"는 약속을 먼저 적고, 그 약속이 지켜지는지 스테이징에서 주기적으로 확인하는 테스트**를 만들기 시작했습니다. 약속 목록은 레포에 파일로 두고, 깨진 약속은 같은 Slack과 PR 흐름으로 보고됩니다. 마켓플레이스에는 이 결과를 여러 관점에서 다시 검토하는 플러그인(`op-promise-review`)을 추가했습니다. 에러가 나지 않는 문제도 에이전트가 볼 수 있는 신호로 만드는 것이 목표입니다.

## 마치며

이 작업의 출발점은 "알림이 왔을 때 원인만큼은 빨리 알고 싶다"는 작은 불편이었습니다. 그리고 사실 이게 될까라는 생각으로 실험적인 목적도 있긴 했습니다.

돌아보면 에이전트가 가장 크게 바꾼 것은 원인 조사 과정 자체의 출발점이었습니다. 또 누가 조사했는지와 상관없이 팀 전체가 같은 정보를 보고 판단할 수 있게 된 것도 큰 변화였습니다.

결과적으로는 원하던 목적을 달성했고 팀 내 만족도도 높았습니다. 그러나 개선의 여지도 분명히 존재했습니다.

복잡한 로직을 파악하고 원인을 정확하게 추적해야 하는 정확도와 사내 정책이나 히스토리를 어떻게 컨텍스트로 제공해야 할지, 또 에이전트의 역할을 어디까지 부여해야 통제 가능할지 등 많은 고민을 더 하게 되었던 것 같습니다.

개인적으로 하네스를 구축해서 개발을 하고 있지만 위와 같은 고민은 AI 기반 개발로 전환하게 되면서 늘 숙제로 남는 문제인 것 같습니다.

그래서 에이전트를 어떻게 평가할지, 개선 전후 비교는 어떻게 측정할 것인지에 대한 공부를 해 볼 생각입니다.
